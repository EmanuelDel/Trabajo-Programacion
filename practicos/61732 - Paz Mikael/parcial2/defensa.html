1. Arquitectura y Tecnologías del Sistema

El sistema fue desarrollado bajo un enfoque integral cliente-servidor con estricta validación en el backend y persistencia persistente transaccional:

  • Frontend: Single Page Application (SPA) en React 18, modular, con cálculo en vivo de subtotales y total general, gestión de estado local para el borrador de venta, emisión e impresión de comprobantes en un clic.
  • Backend: Servidor Express en Node.js estructurado con TypeScript, middlewares de autenticación, control de accesos basado en roles (RBAC) y un gestor centralizado de excepciones con respuestas HTTP estandarizadas.
  • Base de Datos: SQLite configurado con modo WAL (Write-Ahead Logging) y claves foráneas habilitadas, operado a través de Drizzle ORM y better-sqlite3 para asegurar concurrencia y transacciones atómicas.

2. Decisiones de Diseño y Fundamentos

A. Importes en Centavos Enteros (Evitar Errores de Punto Flotante)

En computación tradicional, las operaciones matemáticas con números decimales (estándar IEEE 754) sufren pérdidas de precisión (ejemplo: 0.1 + 0.2 = 0.30000000000000004). En un sistema comercial, esto provoca centavos fantasmas y descuadres en auditorías.

Fundamento técnico: Todos los precios, subtotales, totales y pagos se almacenan y procesan en la base de datos y la API como enteros en centavos (ej. $ 6.500,00 se envía como 650000). La interfaz es la única encargada de formatearlo visualmente dividiendo por 100.

B. Transaccionalidad Atómica (ACID en Ventas y Cobranzas)

Al registrar una venta interactúan cuatro tablas al mismo tiempo: ventas, detalles_venta, movimientos_stock y productos. Si se descuenta el stock pero falla el insert del comprobante, el inventario quedaría corrupto.

Fundamento técnico: Se utiliza sqlite.transaction(). Si un producto no tiene stock suficiente o la base de datos encuentra un conflicto, toda la operación se aborta automáticamente (Rollback), dejando la base en su estado intacto previo.

C. Inmutabilidad Histórica de Comprobantes

Si un comprobante hiciera referencia al producto solo por ID y mostrara el precio consultando la tabla productos, cualquier cambio de precio futuro alteraría las ventas del mes pasado.

Fundamento técnico: En la tabla detalles_venta se realiza una copia histórica exacta de la descripción y del precio unitario al momento del cierre de la operación. De esta forma, el comprobante es inmutable en el tiempo.

D. Saldo Derivado en Cuenta Corriente

Fundamento técnico: El saldo de un cliente no es una columna editable sujeta a condiciones de carrera, sino una propiedad calculada: Saldo = Total Ventas en Cta Cte - Total Pagos Registrados. Además, se prohíben pagos superiores al saldo adeudado mediante validación previa en la transacción de cobro.

4. Machete de Respuestas para el Coloquio Oral

1 ¿Qué ocurre si dos usuarios intentan vender al mismo tiempo la última unidad de un producto?

Respuesta sugerida: "La venta se ejecuta dentro de una transacción atómica. La primera solicitud que complete la comprobación descontará la unidad. Cuando la segunda solicitud intente ejecutarse, encontrará que las existencias son insuficientes y el servidor lanzará un error HTTP 409 Conflict (STOCK_INSUFICIENTE). La transacción hace un rollback total, por lo que no se crea el comprobante ni queda descontado nada."

2 ¿Por qué un cliente no puede pagar de más en su cuenta corriente?

Respuesta sugerida: "En POST /api/clientes/:id/pagos, antes de insertar el pago, el backend calcula el saldo adeudado real. Si el importe enviado supera la deuda, responde 409 Conflict con el código PAGO_EXCEDE_SALDO. Esto evita cuentas corrientes con saldos a favor inconsistentes en este modelo de negocio."

3 ¿Cómo garantizaste que al crear un cliente nuevo durante una venta no se pierdan los productos cargados?

Respuesta sugerida: "En el cliente React, el borrador de la venta vive en el estado local (itemsVenta). Al tocar '+ Nuevo cliente', se levanta una ventana modal. Cuando se guarda el nuevo cliente mediante POST /api/clientes, la respuesta nos entrega su nuevo ID, lo seleccionamos en el combo y cerramos el modal. El array de productos en el estado jamás se reinicia."

4 ¿Dónde y cómo se protegen las rutas que solo debe usar el Administrador?

Respuesta sugerida: "En el servidor mediante el middleware requerirAdmin. Aunque una persona intente utilizar Postman o curl para invocar POST /api/usuarios, el middleware lee la cookie de sesión cifrada, consulta el usuario en la base de datos y, si su campo administrador es falso, interrumpe la ejecución con un código 403 Forbidden."

5 Si desactivo un producto, ¿qué ocurre con los comprobantes emitidos en el pasado?

Respuesta sugerida: "La baja es lógica (columna activo = false). El producto deja de figurar como opción en las nuevas ventas, pero su registro sigue en la base de datos, por lo que los comprobantes antiguos conservan todas sus relaciones foráneas y su histórico intacto."
